# 宝宝辅食排敏小程序 - 技术架构文档

## 1. 技术栈选择

### 1.1 前端技术
- **开发框架**：微信小程序原生开发框架
- **编程语言**：JavaScript
- **样式语言**：WXSS (微信小程序样式语言)
- **模板语言**：WXML (微信小程序模板语言)
- **组件化**：使用微信小程序自定义组件

### 1.2 后端技术
- **云开发平台**：微信云开发（独立环境，与打卡功能隔离）
- **数据库**：云数据库 (NoSQL，独立集合)
- **云函数**：Node.js（独立云函数目录）
- **云存储**：用于存储宝宝照片等媒体资源

### 1.3 开发工具
- **微信开发者工具**
- **版本控制**：Git

## 2. 系统架构设计

### 2.1 整体架构图
```
┌─────────────────────┐     ┌─────────────────────┐     ┌─────────────────────┐
│      排敏前端       │     │      云开发         │     │      云数据库       │
│   (微信小程序)      │◄───►│      服务端         │◄───►│                     │
└─────────────────────┘     └─────────────────────┘     └─────────────────────┘
```

### 2.2 架构特点
- **完全独立**：与打卡功能无任何交互，独立运行
- **前后端分离**：前端负责UI渲染和用户交互，后端负责数据处理和业务逻辑
- **无服务器架构**：使用微信云开发，无需搭建和维护服务器
- **云原生**：充分利用微信云开发的各项能力
- **实时数据同步**：支持数据的实时监听和更新

## 3. 开发方案

### 3.1 前端开发方案

#### 3.1.1 页面结构
- **排敏首页 (sensitivity/index)**：展示排敏推荐和进度
- **宝宝信息页 (sensitivity/baby-info)**：填写和管理宝宝信息
- **排敏记录页 (sensitivity/record)**：记录每日排敏情况
- **已排敏管理页 (sensitivity/manage)**：管理已排敏食物
- **排敏记录列表页 (sensitivity/history)**：查看历史排敏记录

#### 3.1.2 组件规划
- **FoodItem**：食物推荐卡片组件
- **ProgressBar**：排敏进度条组件
- **BabyInfoForm**：宝宝信息表单组件
- **AllergySelect**：过敏反应选择组件
- **LikeSelect**：喜好程度选择组件

#### 3.1.3 状态管理
- 使用微信小程序全局状态管理机制 (`globalData`) 管理宝宝信息
- 页面间数据传递通过路由参数实现
- 避免与打卡功能的状态共享

#### 3.1.4 网络请求
- 使用微信小程序的 `wx.cloud.callFunction` 调用独立的排敏云函数
- 使用微信小程序的 `wx.cloud.database` 直接操作排敏相关的数据库集合

### 3.2 后端开发方案

#### 3.2.1 云函数设计
- **sensitivity-get-baby-info**：获取宝宝信息
- **sensitivity-save-baby-info**：保存宝宝信息
- **sensitivity-get-recommendations**：获取排敏推荐食物
- **sensitivity-save-record**：保存排敏记录
- **sensitivity-get-progress**：获取排敏进度
- **sensitivity-get-history**：获取排敏历史记录
- **sensitivity-update-completed**：更新已排敏食物

#### 3.2.2 数据库设计
- **sensitivity_babies**：宝宝信息集合
- **sensitivity_foods**：排敏食物分类集合
- **sensitivity_records**：用户排敏记录集合
- **sensitivity_progress**：排敏进度集合

#### 3.2.3 安全与权限
- 使用微信云开发的安全规则进行数据库访问控制
- 实施基于用户身份的权限管理
- 确保与打卡功能的数据隔离

## 5. 关键技术点

### 5.1 排敏推荐算法实现
- **推荐顺序算法**：按照排敏顺序（0-100从小到大）推荐未排敏食物
- **分类完成逻辑**：实现分类下3种食物完成后自动标记分类完成的功能
- **排敏天数计算**：实现不同过敏等级食物的排敏天数累计和判断

### 5.2 过敏反应处理逻辑
- **不过敏处理**：继续累计排敏天数，完成后标注为已完成
- **轻微过敏处理**：自动延长2天排敏天数，继续高优推荐；若连续3天标注轻微过敏，则不再推荐
- **重度过敏处理**：立即停止该食物排敏，不再推荐

### 5.3 数据隔离与安全
- **命名空间隔离**：所有排敏相关文件、函数、集合都使用`sensitivity-`前缀
- **数据访问控制**：通过数据库安全规则限制用户只能访问自己的排敏数据
- **无交叉引用**：确保排敏代码不引用任何打卡相关的代码和数据

### 5.4 性能优化
- **列表渲染优化**：使用虚拟列表处理大量食物数据
- **数据缓存优化**：缓存宝宝信息和已排敏食物，减少网络请求
- **算法效率优化**：优化推荐算法，减少计算时间
- **资源加载优化**：使用分包加载，优化小程序启动速度

## 10. 技术风险评估

### 10.1 已知风险
- 排敏推荐算法的复杂度可能影响性能
- 食物分类和排敏规则的变更可能需要重构代码
- 大量数据下的性能表现可能不佳

### 10.2 风险缓解措施
- 优化推荐算法，减少计算复杂度
- 设计灵活的数据结构，支持分类和规则的动态配置
- 优化数据查询和渲染逻辑，分批加载大量数据

### 11.3 注释规范

- 组件和函数需要文档注释
- 复杂逻辑需要行内注释

### 11.4 版本控制规范

## 12. 数据隔离规范

### 12.1 命名空间隔离
- 所有排敏相关的文件、函数、集合都必须使用`sensitivity-`前缀
- 避免与打卡功能的命名冲突

### 12.2 代码隔离
- 排敏代码不允许引用任何打卡相关的代码
- 打卡代码不允许引用任何排敏相关的代码

### 12.3 数据隔离
- 排敏数据不允许存储在打卡相关的数据库集合中
- 打卡数据不允许存储在排敏相关的数据库集合中

### 12.4 功能隔离
- 排敏功能与打卡功能之间不允许有任何交互
- 用户在排敏Tab和打卡Tab之间切换时，数据互不影响
